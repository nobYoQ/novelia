# 文档维护

[维护目录](README.md) · [文档首页](../README.md)

文档的目标是让开发者知道系统怎样工作、改动应该落在哪一层，以及哪些行为必须保留。先解释问题和流程，再给必要的字段、路径和测试入口；不要逐行翻译源码。

## 每种内容放在哪里

| 内容 | 主要位置 |
| --- | --- |
| 产品介绍、下载与简短构建入口 | 根 README |
| 环境、构建和常见扩展步骤 | development |
| 生命周期、状态流、导航和公共组件 | architecture |
| 用户操作及对应业务规则 | features |
| 持久化、文档格式和恢复 | data |
| 认证、API、同步和传输 | network |
| 测试、性能和安全边界 | quality |
| 发布、排障、文档规则和历史材料 | maintenance |

一条规则保留一个主要说明位置，其他页面链接过去。例如，功能页解释“为什么这个操作显示待同步”，网络页解释重放策略，数据页解释什么时候落盘。

## 一篇开发文档怎样写

开头用一段话说明用途和核心关系。正文按读者的任务组织：入口、流程、关键规则、失败或兼容情况，最后给源码与测试入口。

用连续短段落解释因果，用表格比较真正平行的对象，用图表达跨层流程。文件清单只保留定位所需入口，不复制整棵源码树。颜色、间距和临时测试数量通常不必逐项记入功能正文。

需要精确解释的内容不能省略，例如账号归属、持久化时机、阅读坐标、删除范围、冲突处理和不可重放的写操作。读者应能据此做正确修改，而不是只看到“注意边界”。

## 怎样避免过时

- 先核对入口与实际实现，按钮文字、注释和旧文档不能单独证明行为。
- 版本优先链接 version.properties，工具链链接实际 Gradle/原生配置；避免在多处写“当前版本”。
- 测试类链接表示可运行的入口，不表示已经执行。结果写清提交、日期和环境，历史部署记录与当前协议分开。
- 说明本地验证的范围。源码检查不能证明当前线上部署、真实设备或 GitHub 后台设置。
- 发现实现问题就明确写成现存限制，不把计划行为写成已完成，也不为让文档看起来正常而隐藏故障。

## 文件和链接

使用 UTF-8 无 BOM、简体中文、小写英文文件名，目录入口用 README.md。链接相对当前文档，源码路径指向仓库中确实存在的文件；不要链接只在某台电脑存在的输出作为长期依据。

移动页面时更新总目录、分类入口及正文引用；改标题时检查锚点。历史文档标明时间范围，并提供当前说明入口。

## 命令与提交检查

命令默认从仓库根执行，Windows 使用 PowerShell 7。优先采用项目脚本，例如：

```powershell
./build.ps1 -Tasks @(':app:testDebugUnitTest', '--tests', 'cc.novelia.app.data.network.ApiContractTest')
```

说明前提、产物和副作用；联网、设备及发布操作保留显式开关。示例不包含真实凭据，不混用 Bash 转义。

提交前核对本地链接和标题锚点、源码路径、命令语法、代码围栏、中文编码与空白。运行：

```powershell
git diff --check
```

它只检查补丁空白，不能代替链接和内容核对。纯文档修改通常不需要重建应用；若同时改了脚本、配置或生产代码，按[测试指南](../quality/testing.md)补相应检查。

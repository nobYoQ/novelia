# 文档分类与维护规则

[返回发布与维护索引](README.md) · [文档总目录](../README.md)

文档用于解释当前客户端的行为、设计约束和维护方法。描述以当前工作区实现为依据；功能说明、计划和实际测试结果需要明确区分，不能把文档中的操作示例当成已执行记录。

## 1. 按职责选择位置

```text
docs/
├── README.md              总入口与阅读路线
├── development/           环境搭建、构建与开发流程
├── architecture/          分层、源码布局、UI 与导航约束
├── features/              用户可见功能及业务流程
├── data/                  模型、落盘、备份与恢复
├── network/               认证、请求、缓存与云端同步
├── quality/               测试、性能、安全和隐私
└── maintenance/           发布、排障及文档维护
```

| 要补充的内容 | 首选位置 |
| --- | --- |
| 新的书架操作、阅读入口或社区行为 | `features/` 对应功能专题 |
| 功能跨越多个页面但有同一用户目的 | 在同一功能专题串起流程，链接相应底层文档 |
| 共享导航、弹层、Markdown 或交互组件 | `architecture/ui-and-navigation.md` |
| 数据字段、持久化、文件生命周期 | `data/`，引用模型和存储实现 |
| 新接口、鉴权、离线重试和账号隔离 | `network/` |
| 测试选择、基准条件、隐私边界 | `quality/` |
| 日常构建与贡献步骤 | `development/` |
| 发行操作、故障定位、文档规则 | `maintenance/` |

目录按读者寻找问题的方式分类，不要求与 Kotlin package 一一对应。文档内部再通过[源码目录导航](../architecture/source-layout.md)定位实现。新增专题要加入所属目录的 `README.md`，必要时加入总目录的功能查找表。

## 2. 功能专题应包含什么

适合采用以下顺序，并按实际复杂度取舍：

1. 功能入口、适用对象，以及关联功能。
2. 核心数据及归属：设备共享、单书、账号、内存还是磁盘。
3. 正常流程：用户操作如何进入 UI、数据层、文件或网络层。
4. 冲突、失败、取消、恢复和生命周期边界。
5. 限制及尚未支持的行为，区分当前实现与未来计划。
6. 源码入口、已有回归测试及仍需设备确认的场景。

复杂时序适合用简短 Mermaid 图，条件和行为对照适合表格。不要逐行翻译源码，也不要用只包含文件列表的页面代替功能说明。

例如书架专题解释移除条目会发生什么；状态落盘顺序归数据专题；收藏请求如何带账号归网络专题。每项规则保留一个主要说明位置，通过相对链接互相引用，降低多份描述逐渐不一致的风险。

## 3. 以实现为依据

- 先阅读调用入口和实际实现，再描述行为；按钮文字、函数名和注释都不能单独证明完整语义。
- 对范围说明具体边界，例如当前页搜索、已缓存正文搜索、整个本地文档搜索，避免笼统写成“支持全文搜索”。
- 区分客户端权限判断与服务端授权、内存更新与磁盘提交、本地移除与远端删除、任务完成与文件已导入。
- 数值和版本优先链接其配置来源。必须重复限额时写明所属入口，相关实现变动时一起检查。
- 测试类链接表示可供维护者选择的入口，不代表该测试已运行，也不代表覆盖了旁边所有场景。
- 来自历史记录的测试结果需要附时间、提交与环境；不能长期当作项目当前状态。

当前 README、贡献规范、发布操作和素材许可各有独立职责；从总目录链接这些根目录文件，不复制整篇内容。

## 4. 文件与链接约定

文件使用 UTF-8 无 BOM。专题文件名使用小写英文单词和连字符，目录入口统一为 `README.md`；正文默认简体中文，类型名、字段名和命令保留源码写法。

链接使用相对于当前文档的路径。在 `docs/features/` 等二级目录中：

```markdown
[同目录专题](reader.md)
[其他分类](../data/data-and-storage.md)
[仓库文件](../../CONTRIBUTING.md)
[源码](../../app/src/main/java/cc/novelia/app/data/storage/LocalStore.kt)
```

以上是路径写法示例，具体目标应与所在文档相符。移动页面时同步更新总目录、分类目录、根 README、贡献/发布文档、benchmark 说明及正文中的相互引用。若标题变化，还要检查指向标题的锚点。

不要写个人电脑的绝对路径，不要链接只存在于本机的 `build/`、日志或签名文件作为长期文档依赖。API URL 示例只使用公开地址和占位符，不包含用户凭据或真实私有数据。

## 5. 命令示例

构建命令以仓库根目录为执行位置，使用项目提供的 PowerShell 7 入口。涉及参数列表时保留 PowerShell 数组形式：

```powershell
./build.ps1 -Tasks @(':app:testDebugUnitTest', '--tests', 'cc.novelia.app.ApiContractTest')
```

命令下方解释用途、前提与输出位置。可选联网联调、设备测试及发行操作应指向各自完整说明，不能省掉显式开关。不要把 Bash 的反斜杠续行或引号转义混入 PowerShell 示例。

## 6. 提交前检查

文档变更至少核对以下内容：

- 所有页面可从总目录经分类入口到达，无遗漏孤立页面。
- 相对链接目标存在，跨分类路径和标题锚点正确；代码块里的路径示例也应符合说明。
- 新增字段、限制、流程和源码中实际行为一致，关联专题没有相反描述。
- Markdown 表格、代码围栏和 Mermaid 图结构完整，中文编码正常，无 BOM 或行尾空白。
- 移动后的旧路径不再被仓库其他文档引用，原有用户内容没有被静默丢弃。

可先在仓库根检查文件及补丁格式：

```powershell
rg --files docs
git diff --check
```

`git diff --check` 不会验证链接目标、未跟踪文件或行为描述，需要另外核对。纯文档改动一般不要求重跑应用全量构建；若同时修改命令脚本、配置或生产代码，应按[测试指南](../quality/testing.md)执行对应检查。
